# 文档更新指南

> **文档说明**：本指南用于规范文档更新流程,确保文档状态同步准确,减少重复工作。

**最后更新**：2025-11-08

---

## 🎯 核心原则

### 单一数据源原则 (Single Source of Truth)

每个信息只在一个地方维护,其他文档引用该信息:

| 信息类型 | 唯一数据源 | 其他文档处理 |
|---------|-----------|------------|
| 需求列表/状态统计 | `requirements/README.md` | - |
| 需求概览（简短） | `requirements/README.md` | - |
| 任务状态/工时/完成度 | `tasks/README.md` | PROJECT-STATUS 引用汇总 |
| **Issue状态/工时/统计** | **`issues/README.md`** | **PROJECT-STATUS 引用汇总** |
| 当前阻塞问题 | `00-PROJECT-STATUS.md` | - |
| 待办清单 | `00-PROJECT-STATUS.md` | - |
| 关键决策 | `00-PROJECT-STATUS.md` | TASK 文档可记录任务级决策 |
| 任务详细信息 | `TASK-00X.md` | - |
| **Issue详细信息** | **`ISS-XXX.md`** | **-** |
| 技术方案 | `技术方案设计.md` | - |

### 精简记录原则

- ✅ **记录关键信息**：决策、问题、成果、经验
- ❌ **不记录详细过程**：逐步执行日志、详细操作步骤
- 📁 **详细日志归档**：如需保留,放入 `archive/` 目录

## 📋 文档更新流程

### 更新场景说明

**任务级更新**（完成单个任务时）：
- Step 1: 更新 `tasks/README.md`
- Step 2: 更新 `00-PROJECT-STATUS.md`
- Step 3: 更新 `TASK-00X.md`

**Issue级更新**（创建/修复 Issue 时）：
- Step A: 创建 `ISS-XXX.md`
- Step B: 更新 `issues/README.md`
- Step C: 更新 `00-PROJECT-STATUS.md`
- Step D: Issue 修复完成后更新

**需求级更新**（需求状态变更或完成时）：
- Step 4: 更新 `requirements/README.md`

## 📋 创建/修复 Issue 时的更新清单

> **Issue** 是需求执行中发现的**计划外问题**（Bug、功能增强、优化等），与计划内的 Tasks 互补。

### Issue 级更新时机
- **创建 Issue**: 发现 Bug、用户反馈功能缺失、需要性能/安全优化时
- **修复 Issue**: Issue 修复完成、测试通过后
- **关闭 Issue**: Issue 已验收或决定不修复时

### Step A: 创建 Issue 文档 (5分钟)

**操作位置**: `docs/requirements/REQ-XXX/issues/ISS-XXX-问题名.md`

1. 确认需要创建 Issue（参考 issues/README.md 中的"何时创建 Issue"）

| Step C | PROJECT-STATUS.md | 2分钟 | 添加到 Issues 跟踪表、更新待办 |
| Step D | 3个文档 | 5分钟 | 修复完成后更新状态、工时、测试结果 |
| **Issue级小计** | **3个文档** | **14分钟** | 创建9分钟 + 修复后5分钟 |

### 需求级更新
| 步骤 | 更新文档 | 预估时间 | 主要操作 |
|------|---------|---------|---------|

| **需求级小计** | **1个文档** | **2分钟** | - |

### 总计
- **任务完成时更新**: 10分钟（3个文档）
- **Issue完成时更新**: 14分钟（3个文档）
- **需求完成时更新**: 2分钟（1个文档）

## ❌ 不要做的事

### 1. 不要在多个文档重复记录同一信息
- ❌ **错误**: 在 TASK 文档、PROJECT-STATUS、执行记录.md 都详细记录执行过程
- ✅ **正确**: 任务状态只在 tasks/README.md 维护,PROJECT-STATUS 引用汇总

### 2. 不要记录详细执行日志
- ❌ **错误**: 在 TASK 文档记录"步骤1、步骤2、步骤3..."的详细过程
- ✅ **正确**: 只记录关键决策、重要问题、最终成果

### 3. 不要记录一般性问题
- ❌ **错误**: 每个小问题都记录在文档中
- ✅ **正确**: 只记录影响任务的重要问题

### 4. 不要创建和维护执行记录.md
- ❌ **错误**: 创建2000+行的详细执行日志
- ✅ **正确**: 用 PROJECT-STATUS.md 记录关键信息,详细日志归档到 archive/

## 📚 常见问题

### Q1: 是否还需要执行记录.md？
**A**: 不需要。用 `00-PROJECT-STATUS.md` 代替。如果需要保留详细日志,可以创建 `archive/执行记录-详细日志.md`,但不作为主要文档。

### Q2: 任务执行过程中的详细步骤应该记录在哪？
**A**: 不需要记录详细步骤。只记录：
- 关键决策（为什么这样做）
- 重要问题（遇到了什么障碍）
- 最终成果（交付了什么）
- 经验教训（学到了什么）

### Q3: 如何避免文档状态不一致？
**A**: 遵循"单一数据源"原则：
- 需求列表/状态 → 只在 `requirements/README.md` 维护
- 任务状态 → 只在 `tasks/README.md` 维护
- PROJECT-STATUS → 从 tasks/README.md 汇总引用
- 不要在多处重复填写同一信息

### Q4: 项目完成后应该保留哪些文档？
**A**: 必需保留：
- ✅ 需求文档.md (需求文档)
- ✅ 技术方案设计.md
- ✅ 00-PROJECT-STATUS.md (项目总结)
- ✅ tasks/README.md
- ✅ TASK-00X.md (所有任务)

可选保留：
- ⚪ archive/ (详细日志)
- ⚪ 迁移总结报告.md (交付文档)

### Q5: 什么时候需要更新 requirements/README.md？
**A**:
- 创建新需求时：添加到需求列表，更新统计
- 需求状态变更时：更新表格状态和统计数字
- 需求完成时：更新状态、填写核心成果
- 不需要频繁更新：只在需求级别的关键节点更新

### Q6: 多人协作时如何更新文档？
**A**:
1. 每人只更新自己负责的任务文档
2. PROJECT-STATUS 由项目负责人或 AI 助手汇总更新
3. requirements/README.md 由项目负责人统一维护
4. 更新时注明"最后更新人"和"最后更新时间"
5. 重要决策应明确标注决策人

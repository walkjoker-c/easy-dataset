## 一、任务目标 🎯

### 1.1 目标描述
在REQ-003的UI测试中发现,从OBS下载的JSONL格式对话数据文件无法正常上传和处理。本任务旨在:
1. 允许后端接受.jsonl文件上传
2. 识别并提取OBS对话数据格式(payload.history)
3. 将对话内容格式化为可读的user_input/assistant形式
4. 实现1行JSONL = 1个chunk的分块策略

- [x] 后端允许.jsonl文件上传 ✅
- [x] 创建JSONL对话数据提取模块 ✅

- [x] 提取并格式化user_input/assistant对话 ✅
- [x] 1行JSONL生成1个chunk ✅
- [x] JSON解析错误有友好提示 ✅
- [x] 所有代码使用CUSTOM标记 ✅

### 1.3 价值说明
**业务价值**: 使用户能够从OBS直接导入对话数据,无需手动下载和转换,简化工作流程
**技术价值**: 扩展文件处理能力,支持更多数据格式,提高系统灵活性

## 三、实施方案

### 3.1 核心技术方案

**方案1: 自动格式检测**
- 通过检测JSONL第一行是否包含`payload.history`结构来区分OBS对话数据和普通JSONL
- 优点: 自动化,用户无需手动选择
- 缺点: 需要准确的格式检测逻辑

**方案2: 用户手动选择**
- 上传时让用户选择文件类型
- 优点: 准确性高
- 缺点: 增加用户操作步骤

**✅ 采用方案1**: 自动格式检测,简化用户操作

### 3.2 实施步骤

#### Step 1: 修改后端文件格式校验 (0.5h)
**文件**: `app/api/projects/[projectId]/files/route.js`
- 第201-203行添加.jsonl到允许的格式
- 使用CUSTOM标记

#### Step 2: 创建JSONL对话数据提取模块 (1.5h)
**文件**: `lib/custom/obs/jsonl-processor.js` (新建)
- `extractConversationFromLine()`: 从单行JSON提取对话
- `processJSONLContent()`: 处理完整JSONL文件
- `validateJSONLFormat()`: 验证JSONL格式

**核心逻辑**:
```javascript
// 提取单行对话
1. 解析JSON → 2. 获取payload.history.data → 3. 遍历segments
→ 4. 提取in-texts/out-texts → 5. 格式化为"user_input: xxx\n\nassistant: xxx"
```

#### Step 3: 集成到文本分割流程 (1.5h)
**文件**: `lib/file/text-splitter.js`
- 在`splitFileByType()`函数开头添加JSONL判断
- 调用JSONL处理器
- 如果检测到对话格式,返回chunks数组(1行1个chunk)
- 如果不是对话格式,降级到普通文本分块

#### Step 4: 测试验证 (0.5h)
- 从OBS下载JSONL文件
- 上传并分块
- 验证chunks内容格式正确

## 六、重要问题记录

### 问题1: 如何区分OBS对话JSONL和普通JSONL?
- **问题描述**: 需要支持OBS对话数据的特殊处理,同时兼容普通JSONL
- **影响程度**: 🟡 中 - 影响功能设计
- **解决方案**: 通过检测第一行JSON是否包含`payload.history`结构来自动区分
- **状态**: ✅ 已解决
- **经验教训**: 自动格式检测比用户手动选择更友好

### 问题2: JSONL内容如何保持对话完整性?
- **问题描述**: 如果按默认策略分块可能会打断对话
- **影响程度**: 🟢 低 - 用户体验问题
- **解决方案**: 采用1行JSONL = 1个chunk策略,保持每条对话完整
- **状态**: ✅ 已解决
- **经验教训**: 针对特定格式采用特定分块策略

### 问题3: 数据结构路径不匹配
- **问题描述**: 初始代码使用`record.segments`,但实际数据是`record.data.segments`
- **影响程度**: 🔴 高 - 导致无法提取任何对话
- **解决方案**: 添加多路径尝试:`record.data.segments || record.segments`,并添加详细调试日志
- **状态**: ✅ 已解决
- **经验教训**: 处理未知数据格式时,应先添加详细调试日志确认数据结构

### 问题4: 字段名包含特殊字符
- **问题描述**: 字段名是`in-texts`和`out-texts`(带连字符),不能用点号访问
- **影响程度**: 🔴 高 - 导致字段值提取失败
- **解决方案**: 使用方括号语法`segment['in-texts']`代替点号语法
- **状态**: ✅ 已解决
- **经验教训**: JavaScript对象属性包含特殊字符时必须使用方括号访问

### 问题5: 对话格式可读性差
- **问题描述**: 长assistant回复包含Markdown时,难以区分对话边界
- **影响程度**: 🟡 中 - 用户体验问题
- **解决方案**: 使用明显的分隔线`========== USER INPUT ==========`,单空行分隔
- **状态**: ✅ 已解决
- **经验教训**: 格式化输出时要考虑人类可读性,特别是长文本场景

### 问题6: 热加载不生效
- **问题描述**: 修改代码后热加载未更新,导致测试始终失败
- **影响程度**: 🟡 中 - 调试效率问题
- **解决方案**: 删除.next目录,重启开发服务器强制重新编译
- **状态**: ✅ 已解决
- **经验教训**: Next.js API Routes修改后如果热加载不生效,需要完全重启

## 七、经验总结

### 7.1 做得好的地方 ✅
1. **自动格式检测**: 通过`validateJSONLFormat()`函数自动识别OBS对话格式,用户体验好
2. **降级处理**: 非对话格式自动降级到普通分块,保证兼容性
3. **错误处理**: JSON解析失败时返回空字符串,不中断整体处理流程
4. **代码隔离**: 所有代码使用CUSTOM标记,遵循REQ-001最佳实践
5. **精简实施**: 只修改3个文件,新增1个模块,改动最小化
6. **详细调试日志**: 添加数据结构检测日志,快速定位问题
7. **多路径支持**: 同时支持`record.data.segments`和`record.segments`,提高兼容性
8. **用户友好格式**: 使用明显分隔线提高对话可读性

### 7.2 需要改进的地方 ⚠️
1. **性能优化**: 大文件JSONL处理可以考虑流式处理,避免内存溢出(当前方案可能在超大文件时有问题)
2. **格式扩展**: 未来可能需要支持其他JSONL格式,需要更通用的检测机制
3. **调试日志清理**: 生产环境应该减少或移除详细的调试日志
4. **热加载问题**: Next.js API Routes热加载有时不生效,需要手动重启

### 7.3 可复用的方案 🔄
1. **格式自动检测模式**: `validateFormat() → processContent() → fallback`模式可复用于其他格式
2. **CUSTOM标记规范**: 所有定制代码使用统一的CUSTOM START/END标记
3. **降级处理策略**: 特定格式处理失败时自动降级到通用处理
4. **多路径尝试模式**: 使用`path1 || path2 || path3`处理数据结构不确定的场景
5. **调试驱动开发**: 先添加日志确认数据结构,再编写提取逻辑

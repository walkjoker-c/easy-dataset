## 一、方案概述

### 1.1 背景说明

当前系统通过 `/api/projects/employee/[employeeId]` API接口为外部系统提供微服务,使用项目的 `name` 字段存储 `employeeId` 实现项目映射。这导致:
1. 项目名称被长串ID占用,用户体验差
2. name字段职责混乱(既是映射ID又是展示名称)
3. 用户无法自由修改项目名称

本方案通过添加专用的 `externalId` 字段解耦外部系统ID与项目展示名称,实现职责分离。

### 1.2 设计目标

- **核心目标**: 添加 `externalId` 字段实现外部系统映射,释放 `name` 字段为用户可编辑的展示名称
- **性能目标**: 查询性能≤10ms(通过添加唯一索引)
- **质量目标**: 代码覆盖率100%,向后兼容率100%
- **可维护性目标**: 遵循代码隔离原则,定制代码清晰标记

### 1.3 设计原则

- **单一职责**: externalId专注映射,name专注展示
- **向后兼容**: 现有项目和功能不受影响
- **代码隔离**: 遵循"能不改官方代码就不改"原则
- **最小修改**: 影响范围最小化,修改点清晰标记

### 2.2 方案对比

#### 方案A: 添加 externalId 字段(推荐)

- **优点**:
  - 职责清晰,字段语义明确
  - 向后兼容,现有项目externalId为null
  - 扩展性好,支持其他外部系统集成
  - 符合数据库设计最佳实践

- **缺点**:
  - 需要数据库迁移
  - 增加一个字段的存储开销(可忽略)

- **适用场景**: 当前需求及未来可能的多外部系统集成场景

#### 方案B: 使用复合键(employeeId + name)

- **优点**:
  - 不需要新增字段

- **缺点**:
  - name字段职责仍然混乱
  - 查询复杂度增加
  - 用户体验未改善
  - 不符合单一职责原则

- **适用场景**: 不适用

#### 方案C: 使用JSON字段存储元数据

- **优点**:
  - 灵活性高,可扩展

- **缺点**:
  - 无法建立唯一索引
  - 查询性能差
  - 类型安全性差
  - 维护复杂

- **适用场景**: 不适用

### 2.3 最终选择

**选择**: 方案A - 添加 externalId 字段

**理由**:
1. 符合数据库设计最佳实践(一个字段一个职责)
2. 查询性能最优(可建立唯一索引)
3. 代码可读性和可维护性最好
4. 向后兼容性完美(现有项目externalId为null)
5. 扩展性最强(支持未来多系统集成)

```

   - POST /api/projects/employee/{employeeId} + { name: "xxx" } (可选)
   ↓
2. 员工API端点接收请求,提取 employeeId 和可选的 name 参数
   ↓
3. 调用 getProjectByExternalId(employeeId)
   ↓
4. Prisma 查询: db.projects.findUnique({ where: { externalId: employeeId } })
   ↓
5a. 项目存在:
   ├→ 如果传入了 name 参数 → 更新项目名称
   └→ 重定向到 /projects/{projectId}/text-split
   ↓
5b. 项目不存在 → 执行流程2(创建新项目)
```

#### 流程2: 创建员工训练项目

```
1. 员工API判断项目不存在
   ↓
2. 确定项目名称:
   - 如果请求中传入了 name 参数 → 使用传入的名称
   - 否则 → 调用 generateFriendlyProjectName(employeeId)
   ↓
3. 调用 createProjectWithExternalId({
     externalId: employeeId,
     name: customName || generatedName,
     description: `数智员工的训练项目`
   })
   ↓
4. 生成友好名称格式: "员工项目-{后8位ID}-20251108"
   示例: "员工项目-174000-20251108"
   ↓
5. 创建项目 + 设置默认模型配置
   ↓
6. 重定向到 /projects/{newProjectId}/text-split
```

#### 流程3: 用户编辑项目名称

```
1. 用户在项目设置页面编辑 name 字段
   ↓
2. 前端调用 PUT /api/projects/{projectId}
   ↓
3. 后端更新 Projects.name (externalId 不变)
   ↓
4. 外部系统下次访问时仍通过 externalId 正确映射
   ↓
5. 用户看到的是自定义的友好名称
```

### 4.3 核心算法

#### 算法1: 生成友好项目名称

- **用途**: 为员工项目生成可读的默认名称,包含部分ID和时间戳便于识别
- **复杂度**: 时间复杂度 O(1), 空间复杂度 O(1)
- **算法实现**:
  ```javascript
  function generateFriendlyProjectName(employeeId) {
    // 提取employeeId后8位(或更短)
    const idSuffix = employeeId.slice(-8);

    // 生成日期时间戳 (格式: YYYYMMDD)
    const timestamp = new Date().toISOString()
      .slice(0, 10)           // "2025-11-08"
      .replace(/-/g, '');     // "20251108"

    return `员工项目-${idSuffix}-${timestamp}`;
  }
  ```

- **示例**:
  - 输入: `"employee-123e4567-e89b-12d3-a456-426614174000"`
  - 输出: `"员工项目-14174000-20251108"`

  - 输入: `"emp-001"`
  - 输出: `"员工项目-emp-001-20251108"`

- **设计考虑**:
  - ✅ 包含部分ID: 便于关联原始employeeId
  - ✅ 包含日期: 便于识别创建时间
  - ✅ 简洁可读: 长度适中,易于理解
  - ✅ 允许重复: name字段不强制唯一,通过projectId区分

#### 算法2: 项目名称重复处理策略

- **背景**: name字段从映射ID改为展示用途后,需要处理重复性问题
- **设计决策**: 允许name字段重复,通过projectId唯一标识项目

**修改点1: 移除API层的唯一性检查**

**设计理由**:

- ✅ 所有查询通过projectId,不受name重复影响

**实现**:
```javascript
// lib/custom/employee-project.js (新文件)
'use server';

import { db } from '@/lib/db/index';
import { createProject } from '@/lib/db/projects';
import { createInitModelConfig } from '@/lib/db/model-config';
import { MODEL_PROVIDERS, DEFAULT_PROJECT_MODEL_PROVIDER_ID } from '@/constant/model';
import { nanoid } from 'nanoid';

/**
 * 通过外部系统ID查找项目
 * @param {string} externalId - 外部系统ID (如employeeId)
 * @returns {Promise<Project|null>}
 */
export async function getProjectByExternalId(externalId) {
  try {
    return await db.projects.findUnique({
      where: { externalId: externalId }
    });
  } catch (error) {
    console.error('Failed to get project by externalId:', error);
    return null;
  }
}

/**
 * 生成友好的项目名称
 * @param {string} employeeId - 员工ID
 * @returns {string}
 */
export function generateFriendlyProjectName(employeeId) {
  // 提取employeeId后8位
  const idSuffix = employeeId.slice(-8);

  // 生成日期时间戳 (YYYYMMDD)
  const timestamp = new Date().toISOString()
    .slice(0, 10)           // "2025-11-08"
    .replace(/-/g, '');     // "20251108"

  return `员工项目-${idSuffix}-${timestamp}`;
}

/**
 * 创建带外部ID的项目
 * @param {Object} data - 项目数据
 * @param {string} data.externalId - 外部系统ID
 * @param {string} [data.name] - 项目名称(可选,自动生成)
 * @param {string} [data.description] - 项目描述
 * @returns {Promise<Project>}
 */
export async function createProjectWithExternalId(data) {
  const { externalId, name, description } = data;

  // 生成友好名称
  const projectName = name || generateFriendlyProjectName(externalId);
  const projectDescription = description || `数智员工的训练项目`;

  // 创建项目
  const project = await createProject({
    name: projectName,
    description: projectDescription
  });

  // 更新 externalId
  const updatedProject = await db.projects.update({
    where: { id: project.id },
    data: { externalId: externalId }
  });

  // 创建默认模型配置 (复用现有逻辑)
  const defaultProvider = MODEL_PROVIDERS.find(p => p.id === DEFAULT_PROJECT_MODEL_PROVIDER_ID);
  if (defaultProvider) {
    const defaultModelConfig = {
      id: nanoid(12),
      projectId: updatedProject.id,
      providerId: defaultProvider.id,
      providerName: defaultProvider.name,
      endpoint: defaultProvider.defaultEndpoint,
      apiKey: defaultProvider.defaultApiKey || '',
      modelId: defaultProvider.defaultModels[0] || '',
      modelName: defaultProvider.defaultModels[0] || '',
      type: 'text',
      temperature: defaultProvider.defaultTemperature || 0.7,
      maxTokens: defaultProvider.defaultMaxTokens || 16384,
      topP: 1,
      topK: 0,
      status: 1
    };
    await createInitModelConfig([defaultModelConfig]);

    // 设置默认模型配置ID
    await db.projects.update({
      where: { id: updatedProject.id },
      data: { defaultModelConfigId: defaultModelConfig.id }
    });
  }

  return updatedProject;
}
```

## 七、风险控制

### 7.1 技术风险

| 风险项 | 风险等级 | 缓解措施 | 应急预案 |
|-------|---------|---------|---------|
| 数据库迁移失败 | 低 | 先在开发环境测试,备份数据库 | 恢复备份,回滚代码 |
| 唯一索引冲突 | 低 | 现有项目externalId为null,无冲突 | 检查数据一致性 |
| 查询性能下降 | 低 | 添加唯一索引,优化查询 | 监控慢查询,调整索引 |
| Prisma Client缓存问题 | 低 | 重启开发服务器 | `npm run db:push` 重新生成 |

### 7.2 业务风险

| 风险项 | 风险等级 | 缓解措施 | 应急预案 |
|-------|---------|---------|---------|
| 外部系统集成失败 | 中 | 充分测试,保留原逻辑兜底 | 临时回滚到旧逻辑 |
| 用户误删externalId | 低 | UI设为只读,API层禁止修改 | 数据库恢复 |
| 名称冲突混淆 | 低 | UI清晰标注字段含义 | 用户培训 |

### 7.3 进度风险

| 风险项 | 风险等级 | 缓解措施 | 应急预案 |
|-------|---------|---------|---------|

| 测试时间不足 | 低 | 预留充足测试时间 | 延长测试周期 |

## 一、需求概述 ⭐

### 1.1 核心目标
集成Keycloak鉴权系统,实现基于用户身份的数据集项目访问控制,防止未授权用户通过URL直接访问他人的数智员工数据集项目,确保用户只能访问自己创建的项目。

**(更新: 2025-11-17 v1.3)** 技术方案明确为:
- Token通过**Cookie**传递 (`Cookie: Authorization=<token>`)
- 调用Keycloak **introspect接口**验证Token合法性,直接使用返回的sub字段
- 实现**三步验证**流程(管理员Session验证 + Token合法性验证 + 权限验证)
- 提供本地**管理员账号**和登录页面,无需依赖Keycloak

### 1.2 业务背景
- **现状**:
  - 数据集项目通过 `externalId`(数智员工ID) 映射创建,存储在数据库中
  - 用户从公司平台以嵌入微服务方式访问数据集项目
  - 当前没有任何鉴权机制,任何人获取URL后都可以访问任意项目

- **问题**:
  - **安全风险**: 用户可以从浏览器开发者工具(F12)获取数据集项目的URL
  - **越权访问**: 在新标签页或其他浏览器中直接输入URL,可以访问其他用户的数智员工项目
  - **数据泄露风险**: 用户A可以通过URL访问用户B的数智员工A1/A2/A3的训练数据

- **期望**:
  - 集成Keycloak鉴权,在创建项目时记录用户ID
  - 访问项目时验证用户身份,仅允许项目创建者访问
  - 防止URL分享或直接访问绕过权限控制
  - 提前完成代码改造,等待公司平台侧完成Token传递功能后自动生效

### 1.3 需求来源
- **提出人**: 数据安全和权限控制需求
- **提出日期**: 2025-11-17
- **业务场景**:
  - 用户在公司平台登录后,点击数智员工卡片的"训练集平台"按钮
  - 公司平台携带JWT token跳转到数据集项目(嵌入微服务形式,Token通过Cookie传递)
  - 数据集项目调用Keycloak introspect接口验证Token合法性
  - 从Token的sub字段提取用户ID,创建项目时记录创建者
  - 后续访问时进行两步验证(Token合法性 + 权限匹配),确保只有创建者可以访问

## 二、需求范围

### 2.1 功能需求

#### 核心功能 (更新: 2025-11-17)

1. **Token获取和验证** (原"JWT Token传递和验证",已重写)
   - **传递方式**: Cookie传递 (`Cookie: Authorization=<token>`)
   - **验证方式**: 调用Keycloak introspect接口验证Token合法性
   - **验证接口**:
     - URL: `{KEYCLOAK_INTROSPECT_URL}` (环境变量配置)
     - 示例: `https://apps.dev2.aquaintelling.com/keycloak/realms/jhipster/protocol/openid-connect/token/introspect`
     - Method: POST
     - Content-Type: `application/x-www-form-urlencoded`
     - 请求参数:
       - `token`: JWT token字符串
       - `client_id`: 客户端ID (如 `internal`,环境变量配置)
       - `client_secret`: 客户端密钥 (环境变量配置)
     - 返回: JSON对象,包含 `active` 字段(boolean)表示Token是否有效
   - **验证逻辑**:
     - 从Cookie中提取 `Authorization` 字段获取Token
     - 调用introspect接口验证Token
     - `active: true` → Token有效,进入权限验证流程
     - `active: false` 或 无Token → 返回401 Unauthorized
   - **输入**: HTTP请求Cookie
   - **输出**: 验证成功返回用户ID,验证失败返回401错误
   - **约束**: 依赖Keycloak introspect接口可用性

2. **用户ID提取** (优化: 2025-11-17)
   - **来源**: Keycloak introspect接口返回的 `sub` 字段
   - **调用流程**:
     a. 从Cookie提取Authorization字段 (JWT Token)
     b. 调用Keycloak introspect接口验证Token
     c. 检查返回的 `active` 字段:
        - `false` → Token无效,返回401
        - `true` → Token有效,继续提取用户ID
     d. 从返回的 `sub` 字段提取用户ID
   - **格式**: UUID字符串 (如 `8e7180cc-204c-4f07-a752-6dc208fb26ef`)
   - **优势**: 不需要本地解析JWT,更简单、更安全,只依赖Keycloak API
   - **用途**: 存储到数据库 `createdByUserId` 字段

3. **数据库字段扩展** (已更新格式说明)
   - **表名**: Projects (已存在)
   - **新增字段**: `createdByUserId` (String类型, 可为NULL)
   - **字段说明**:
     - 存储Keycloak用户ID (JWT Token的sub字段)
     - 格式: UUID字符串 (如 `8e7180cc-204c-4f07-a752-6dc208fb26ef`)
     - NULL值: 现有项目保持NULL,新项目记录创建者ID
   - **数据库迁移**:
     - 使用Prisma migrations添加字段
     - 现有数据保持NULL(不做回填)
   - **约束**: 允许NULL,不设置唯一性约束(一个用户可以创建多个项目)
   - **映射关系**: 构建 **项目ID - externalId - user_id** 三者映射关系

4. **创建项目时记录用户ID** (已更新验证流程)
   - **影响接口**: `app/api/projects/employee/[employeeId]/route.js` (POST方法)
   - **流程**:
     a. 从Cookie提取 `Authorization` 字段
     b. 调用Keycloak introspect接口验证Token
     c. Token有效时,从Token的sub字段提取用户ID
     d. **创建项目时**(包括首次访问自助创建场景)存储到 `createdByUserId` 字段
     e. 如果Cookie无Token,返回401 Unauthorized (根据问题1决策,严格模式)

   - **自助创建场景** (首次通过employeeId访问):
     - 用户首次通过employeeId访问,项目不存在,触发自助创建
     - 创建时从Token解析sub字段,存储到createdByUserId
     - 后续该用户再次访问,权限验证通过(sub == createdByUserId)
     - 其他用户访问该employeeId的项目,权限验证失败(sub != createdByUserId)

   - **输入**: employeeId参数 + Cookie中的Token
   - **输出**: 创建项目并关联用户ID
   - **约束**: 强制要求Token (严格模式),无Token返回401

5. **访问项目时三步验证** (重写: 2025-11-17,从两步改为三步)
   - **影响接口**:
     - `app/api/projects/employee/[employeeId]/route.js` (通过employeeId访问)
     - `app/api/projects/[projectId]/route.js` (通过projectId访问)
     - 所有项目相关API接口

   **验证流程**:

   - **步骤1: 管理员身份验证** (优先级最高)
     - 检查 `req.session.isAdmin`
     - 如果为 `true` → **直接允许访问**,跳过步骤2和3
     - 否则 → 进入步骤2

   - **步骤2: Token合法性验证**
     - 从Cookie提取Authorization字段
     - 调用Keycloak introspect接口验证
     - 检查返回的 `active` 字段:
       - `false` → 返回401 Unauthorized
       - `true` → 从返回的 `sub` 字段提取用户ID → 进入步骤3

   - **步骤3: 权限验证**
     - 从数据库查询项目的 `createdByUserId`
     - 判断逻辑:
       - `sub == createdByUserId` → 允许访问
       - `sub != createdByUserId` → 返回403 Forbidden
       - `createdByUserId == NULL` → 允许访问 (现有项目兼容)
       - `createdByUserId == "admin"` → 返回403 (只有管理员能访问)

   - **输入**: projectId/employeeId参数 + Cookie中的Token 或 管理员Session
   - **输出**: 验证通过允许访问,验证失败返回401/403错误
   - **约束**:
     - 管理员可以绕过所有验证访问所有项目
     - 通过employeeId访问和通过projectId访问,鉴权逻辑一致
     - 不影响现有项目的访问(NULL值的项目仍可访问)

6. **错误处理和前端交互** (已更新)
   - **401 Unauthorized**:
     - 触发条件:
       - Cookie中无Token
       - Token无效 (introspect返回 active: false)
       - Token过期
       - Keycloak验证失败
     - 返回: `{ error: "未授权访问,请重新登录", code: 401 }`
     - 前端行为: 显示"请登录"提示或跳转登录页
   - **403 Forbidden**:
     - 触发条件: Token有效,但用户ID不匹配项目创建者
     - 返回: `{ error: "无权访问此项目", code: 403 }`
     - 前端行为: 显示"无权访问该项目"错误页
   - **500 Internal Server Error**:
     - 触发条件:
       - Keycloak服务不可用
       - introspect接口调用失败
       - 数据库查询失败
       - 配置错误
     - 返回: `{ error: "系统错误,请稍后重试", code: 500 }`
     - 前端行为: 显示系统错误提示
   - **约束**:
     - 正常流程下(公司平台已登录),用户应该有有效Token
     - 401主要处理异常情况和未登录场景

7. **Token缓存机制** (保留,可根据introspect接口调整)
   - **目的**: 减少重复调用Keycloak introspect接口,提高响应速度
   - **缓存策略**:
     - 缓存key: Token的SHA256哈希值
     - 缓存value: `{ userId: "xxx", active: true, expiresAt: timestamp }`
     - 缓存时间: 5-30分钟(建议缓存时间 = Token有效期 - 5分钟,或根据introspect返回的exp字段)
   - **缓存失效**:
     - Token过期时间到达
     - 手动清除缓存(如配置变更)
   - **技术选型**: 使用内存缓存(如Node.js Map)或Redis(如有)
   - **约束**:
     - 缓存时间不能超过Token有效期
     - 缓存命中时仍需验证过期时间

8. **环境配置管理** (新增)
   - **支持环境**: dev / test / prod 三个环境
   - **环境变量**:
     - `KEYCLOAK_INTROSPECT_URL`: Keycloak introspect接口地址
       - dev示例: `https://apps.dev2.aquaintelling.com/keycloak/realms/jhipster/protocol/openid-connect/token/introspect`
       - test: 待确认
       - prod: 待确认
     - `KEYCLOAK_CLIENT_ID`: 客户端ID (如 `internal`)
     - `KEYCLOAK_CLIENT_SECRET`: 客户端密钥 (不同环境不同值,严格保密)
   - **配置文件**:
     - 配置示例添加到 `.env.example`
     - 真实配置存储在 `.env.local` (不提交到git)
   - **启动验证**: 应用启动时验证环境变量完整性,缺失则报错

9. **管理员权限 (本地管理员账号)** (重写: 2025-11-17)

   **管理员配置**:
   - 通过环境变量配置管理员密码: `ADMIN_PASSWORD=your_secret_password`
   - 管理员ID固定为: `"admin"`
   - 不依赖Keycloak,使用Session验证

   **管理员登录页面**:
   - 路径: `/admin/login`
   - 功能:
     - 提供密码输入框
     - 验证密码是否等于环境变量 `ADMIN_PASSWORD`
     - 验证成功:
       - 设置Session标记: `req.session.isAdmin = true`
       - 跳转到项目列表页面
     - 验证失败: 显示错误提示
   - 会话管理:
     - Session有效期: 根据服务器Session配置 (如24小时)
     - 退出登录: 清除Session (`req.session.destroy()`)

   **鉴权逻辑** (三步验证):
   - 步骤1: 检查Session中的管理员标记
     - 如果 `req.session.isAdmin === true` → 允许访问所有项目,跳过后续验证
     - 否则 → 进入步骤2

   - 步骤2: Keycloak Token验证 (正常用户流程)
     - 从Cookie提取Token
     - 调用Keycloak introspect验证
     - 提取sub字段
     - 进入步骤3

   - 步骤3: 权限验证
     - 比对sub字段和createdByUserId
     - 判断是否允许访问

   **手动创建项目的处理**:
   - 根目录手动创建的项目,createdByUserId设为 `"admin"`
   - 只有管理员登录后才能访问 (`req.session.isAdmin === true`)
   - 普通用户访问返回403 Forbidden

   **使用场景**:
   - 管理员登录后可访问所有项目 (包括employeeId创建的和手动创建的)
   - 方便系统管理、故障排查、开发测试

   **安全考虑**:
   - 管理员密码通过环境变量配置,不hardcode
   - 使用服务器Session存储管理员状态,不暴露在客户端
   - Session应使用httpOnly Cookie,防止XSS攻击
   - 建议使用强密码,定期更换

   **后续扩展** (V2.0):
   - 可考虑支持Keycloak管理员账号
   - 可考虑支持多个管理员账号
   - 可考虑管理员操作审计日志

10. **管理员登录页面** (新增: 2025-11-17)

   **页面路径**: `/admin/login`

   **页面元素**:
   - 密码输入框 (type="password")
   - 登录按钮
   - 错误提示区域

   **前端逻辑**:
   - 用户输入密码,点击登录
   - 发送POST请求到 `/api/admin/login`
   - 请求体: `{ "password": "用户输入的密码" }`
   - 响应处理:
     - 200 OK → 登录成功,跳转到项目列表页面 (`/`)
     - 401 Unauthorized → 显示"密码错误"
     - 500 Server Error → 显示"系统错误"

   **后端API**: `/api/admin/login`
   - Method: POST
   - 请求体: `{ "password": "..." }`
   - 验证逻辑:
     ```javascript
     if (req.body.password === process.env.ADMIN_PASSWORD) {
       req.session.isAdmin = true;
       return res.status(200).json({ success: true });
     } else {
       return res.status(401).json({ error: "密码错误" });
     }
     ```
   - Session配置:
     - 使用express-session或类似中间件
     - 设置httpOnly: true
     - 设置secure: true (生产环境HTTPS)
     - 设置sameSite: 'strict'

   **退出登录**:
   - 路径: `/api/admin/logout`
   - Method: POST
   - 逻辑: `req.session.destroy()`

## 三、约束条件

### 3.1 技术约束 (更新: 2025-11-17)
- **Keycloak版本**: 必须兼容Keycloak 26.0.4
- **Token传递方式**: Cookie传递 (`Cookie: Authorization=<token>`),不支持其他方式
- **Token验证方式**: 调用Keycloak introspect接口,不自己解析和验证JWT签名
- **用户ID提取**: 直接使用introspect接口返回的sub字段,不本地解析JWT
- **HTTP客户端**: 需要支持POST请求调用introspect接口(如fetch、axios等)
- **环境支持**: 必须支持 dev / test / prod 三个环境,通过环境变量区分配置
- **部署环境**: 内网环境,Keycloak服务和数据集项目在同一内网
- **数据库**: SQLite (Prisma ORM),需支持字段默认值为NULL
- **前端框架**: Next.js 14,需兼容现有前端错误处理逻辑
- **依赖Keycloak服务**: 依赖Keycloak introspect接口可用性,服务不可用时需优雅降级
- **向后兼容**: 采用严格模式,Cookie无Token时返回401
- **管理员认证方式**: Session-based,不使用Keycloak
- **Session管理**: 使用服务器端Session (如express-session)
- **管理员密码**: 通过环境变量配置,不hardcode

  // 查询或创建项目逻辑
  let project = await prisma.project.findFirst({
    where: { externalId: params.employeeId },
  });

  if (!project) {
    // ========== CUSTOM START ==========
    // 定制说明: REQ-004 Keycloak鉴权功能 - 创建项目时记录用户ID

        externalId: params.employeeId,

#### E.4 好处总结

使用代码隔离规范的好处:

1. **版本升级容易** ⭐
   - 官方代码更新时,只需关注 `CUSTOM START/END` 标记的部分
   - 定制代码独立在 `lib/custom/`, `pages/admin/` 等目录,不受影响

2. **合并冲突少**
   - 官方文件修改少,合并冲突概率低
   - 即使冲突,通过 `CUSTOM` 标记快速定位

3. **代码审查清晰**
   - 一眼识别哪些是定制代码
   - 便于团队协作和代码审查

4. **迁移提取方便**
   - 需要迁移到新版本时,可以快速提取所有 `CUSTOM` 标记的代码
   - 可以编写脚本自动提取定制代码

5. **文档追溯**
   - 每处修改都有说明和日期
   - 可以追溯到具体需求编号 (如 REQ-004)

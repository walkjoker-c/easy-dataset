## 一、方案概述

### 1.1 技术目标
1. 保留 1.4.0 定制版本的完整 Git 历史
2. 获取 1.6.0 官方最新代码
3. 建立能够持续跟进官方更新的分支架构
4. 两个版本独立管理,互不影响

### 1.2 总体架构

```
本地目录结构:
/Users/amx/code/easy-dataset/
├── easy-dataset-1.4.0/     (独立Git仓库 - 1.4.0定制版本)
└── easy-dataset-1.6.0/     (独立Git仓库 - 1.6.0官方+定制)

华为云仓库架构:
de-dataset (单一仓库,多分支管理)
├── master               (1.4.0定制版本 - 历史保留)
├── official-upstream    (1.6.0官方代码 - 追踪更新)
└── custom-production    (1.6.0定制开发 - 工作分支)
```

## 三、华为云同步策略

### 3.1 方案对比

| 方案 | 架构 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| A: 双仓库 | 两个独立仓库 | 完全隔离 | 管理复杂 | 长期并行维护 |
| B: 单分支 | 单仓库两分支 | 统一管理 | 易混淆 | 短期过渡 |
| C: 替换 | 仅保留新版 | 简化管理 | 丢失历史 | 完全迁移 |
| **B-Plus: 三分支** | 单仓库三分支 | 隔离清晰+持续跟进 | 需理解分支 | **推荐** |

### 3.2 推荐方案: B-Plus (三分支策略)
在方案B基础上,使用三个分支实现代码隔离与官方同步。详见下文。

## 四、方案B-Plus: 三分支策略

### 4.1 架构设计 ⭐

```
华为云仓库: de-dataset
│
├── master                    # 1.4.0定制版本(已存在,保持不变)
│   └── [你之前的1.4.0改动]
│
├── official-upstream         # 官方代码追踪分支(纯净)
│   ├── 用途: 专门追踪官方GitHub仓库
│   ├── 来源: git fetch origin main
│   └── 规则: 永远不在这个分支上做定制开发
│
└── custom-production         # 定制生产分支(你的工作分支)
    ├── 基于: official-upstream
    ├── 包含: 官方代码 + 你的定制改动
    └── 用途: 实际部署使用的版本
```

### 4.2 分支职责说明

| 分支名称 | 职责 | 来源 | 是否可修改 |
|---------|------|------|-----------|
| master | 1.4.0历史参考 | 历史开发 | ❌ 不再修改 |
| official-upstream | 追踪官方更新 | GitHub官方 | ❌ 仅同步官方 |
| custom-production | 定制开发 | 基于official-upstream | ✅ 日常开发 |

### 4.3 初始设置步骤

```bash
cd /Users/amx/code/easy-dataset/easy-dataset-1.6.0

# 步骤1: 添加华为云remote
git remote add huawei git@codehub-cn-south-1.devcloud.huaweicloud.com:b6c759891eee48fcb55ad994808bdfe9/de-dataset.git

# 步骤2: 创建并推送官方追踪分支
git checkout -b official-upstream
git push -u huawei official-upstream

# 步骤3: 创建并推送定制开发分支
git checkout -b custom-production
git push -u huawei custom-production
```

### 4.4 三分支策略优势

1. **可持续跟进**: 使用 `git merge` 同步官方更新
2. **纯净镜像**: official-upstream保持官方原貌,便于对比
3. **清晰流程**: custom-production专注定制开发
4. **灵活退出**: 如遇困难可切换到方案A
5. **完整历史**: 华为云保留所有版本

## 五、代码隔离最佳实践 ⭐

### 5.1 核心原则

> **能不改官方代码就不改,能用扩展就不修改**

### 5.2 推荐的定制方式

#### ✅ 1. 新增文件而非修改
```
components/custom/MyCustomComponent.js  (✅ 新文件)
lib/custom/myCustomLogic.js             (✅ 新文件)
pages/custom/                           (✅ 新目录)

❌ 避免直接修改 components/原有组件.js
```

#### ✅ 2. 使用配置文件
```javascript
// .env.custom, config/custom.config.js
import customConfig from '@/config/custom.config'
```

#### ✅ 3. 使用插件机制
```
plugins/custom-auth/   plugins/custom-export/   plugins/custom-ui/
```

#### ✅ 4. CSS隔离
```css
/* styles/custom/my-styles.css - 使用CSS Modules */
.custom-container { ... }
/* ❌ 避免修改全局样式 globals.css */
```

### 5.3 必须修改官方文件时的标记规范

```javascript
// ========== CUSTOM START ==========
// 定制说明: 为XXX功能添加YYY逻辑
// 修改日期: 2025-11-05 | 修改人: @yourname
const customLogic = () => { /* 你的定制代码 */ }
// ========== CUSTOM END ==========
```
**好处**: 合并冲突时快速识别、代码审查清晰、迁移时便于提取

## 六、日常工作流程

### 6.1 场景1: 同步官方新版本

```bash
cd /Users/amx/code/easy-dataset/easy-dataset-1.6.0

# 1. 更新官方追踪分支
git checkout official-upstream
git pull origin main
git push huawei official-upstream

# 2. 合并到定制分支
git checkout custom-production
git merge official-upstream

# 3. 解决冲突(如有)
git status  # 查看冲突文件
# 手动解决后: git add . && git commit -m "merge: 合并官方1.7.0更新"

# 4. 测试并推送
npm install && npm run dev
git push huawei custom-production
```

### 6.2 场景2: 添加定制功能

```bash
cd /Users/amx/code/easy-dataset/easy-dataset-1.6.0

# 创建功能分支并开发
git checkout custom-production
git checkout -b feature/my-new-feature
# ... 编写代码 ...
git add . && git commit -m "feat: 添加新功能XXX"

# 合并到主定制分支
git checkout custom-production
git merge feature/my-new-feature
git push huawei custom-production
```

### 6.3 场景3: 处理合并冲突

```bash
git status  # 查看冲突文件
git mergetool  # 使用合并工具

# 手动解决冲突标记: <<<<<<< HEAD vs >>>>>>> official-upstream
# 决策: 保留定制 / 采用官方 / 两者结合

git add <冲突文件>
git commit -m "resolve: 解决合并冲突"
git push huawei custom-production
```

## 七、风险与注意事项

### 7.1 主要风险

| 风险类型 | 解决方案 | 验证方法 |
|---------|---------|---------|
| Git历史丢失 | 保留`.git`目录 | `git log`检查 |
| 分支信息丢失 | `git branch -a`确认 | 对比本地远程列表 |
| Remote关联问题 | `git remote -v`确认 | 尝试fetch/push |
| 合并冲突频繁 | 定期同步+代码隔离+merge工具 | 必要时切换方案A |
| API变更 | 测试+阅读CHANGELOG+重构 | 完整回归测试 |

### 7.2 操作前备份检查清单
1. ✅ 备份完整目录
2. ✅ 确认所有分支已推送远程
3. ✅ 导出定制代码清单
4. ✅ 记录当前commit ID

### 7.3 三分支策略适用场景

**✅ 推荐**: 定制改动少(<10-20文件)、新增为主、有Git经验、需跟进官方
**⚠️ 谨慎**: 大量修改核心代码、差异巨大、经验不足、官方更新频繁

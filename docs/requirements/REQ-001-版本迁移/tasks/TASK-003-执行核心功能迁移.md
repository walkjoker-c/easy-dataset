## 五、关键决策

### 决策1: 标签编辑采用标记修改而非组件包装
**背景**: 原计划使用组件包装模式
**决策**: 改用标记修改(策略5)
**原因**: 1.6.0组件仅78行,非常简单,直接修改更实用
**影响**: 降低代码复杂度,维护成本更低

### 决策2: 禁用Logo点击跳转
**背景**: 原1.4.0版本Logo可点击跳转到主管理界面
**决策**: 注释掉onClick和cursor样式,禁用跳转
**原因**: 后续单用户单项目模式,普通用户不能访问管理员项目列表
**影响**: 增强安全性,符合业务演进方向

### 决策3: 新项目自动包含默认模型配置
**背景**: UI测试发现新项目无法直接使用
**决策**: 修改 `app/api/projects/route.js`,为全新项目创建默认配置
**原因**: 提升用户体验,减少手动配置步骤
**影响**: 员工API创建的项目可直接进入text-split页面

## 六、重要问题记录

### 问题1: 新项目默认模型API Key为空
- **影响程度**: 🟡 中
- **根本原因**: POST `/api/projects` 只在 `reuseConfigFrom` 存在时创建模型配置
- **解决方案**: 添加else分支,从 `DEFAULT_PROJECT_MODEL_PROVIDER_ID` 读取默认提供商
- **状态**: ✅ 已解决
- **经验**: 测试驱动开发,UI测试能发现代码逻辑问题

### 问题2: Logo点击跳转安全隐患
- **影响程度**: 🔴 高 (安全相关)
- **根本原因**: 未考虑业务演进方向和权限隔离需求
- **解决方案**: 注释掉onClick和cursor样式,禁用跳转
- **状态**: ✅ 已解决
- **经验**: 功能迁移时要考虑未来需求和安全性

## 七、经验总结

### 7.1 成功经验
1. **严格遵循代码隔离原则**: 优先使用独立文件,必要修改有明确CUSTOM标记
2. **文档驱动开发**: 创建 CUSTOM_CHANGES.md 实时记录变更
3. **小步快跑,及时验证**: 分批次执行,每个批次独立验证
4. **用户参与测试**: UI测试发现了2个bug和1个改进点
5. **灵活调整策略**: 根据实际情况调整代码隔离策略

### 7.2 关键教训
1. **测试驱动很重要**: UI测试发现了新项目配置缺失和智能跳转需求
2. **考虑安全需求**: 功能迁移应考虑权限隔离和业务演进方向
3. **策略灵活选择**: 根据组件复杂度选择最实用的策略,不拘泥于计划

### 7.3 可复用方案
1. **代码隔离5策略**: 适用于所有定制开发项目
2. **CUSTOM标记规范**: `// CUSTOM: 说明 (迁移自X.X.X)` 格式
3. **分批次迁移策略**: 按优先级和复杂度分批,降低风险
4. **详细Commit模板**: 包含文件变更、业务价值、测试结果
